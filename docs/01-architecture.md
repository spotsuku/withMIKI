# 01. システムアーキテクチャ

本書は WithMIKI を「個人運用の HTML アプリ」から「外販可能なマルチテナント医療 SaaS」へ発展させるためのアーキテクチャを定義する。

---

## 1. 設計原則

1. **共通カルテ基盤 + 対象別モジュール**
   総合（マスター）カルテを全領域共通の土台とし、婦人科・アスリート等の対象別カルテを「ケアプログラム（モジュール）」として上に載せる。新しい対象（整形・内科・小児 等）はスキーマ大改修なしに追加できる。詳細は [02-database-design.md](02-database-design.md)。
2. **テナント分離を最優先**
   1 治療院 = 1 テナント。全テーブルに `tenant_id` を持たせ、PostgreSQL Row-Level Security (RLS) で物理的に分離する。
3. **患者体験の継承**
   現行の「Safari→ホーム画面に追加」「LINE で完結」を壊さない。PWA ＋ LINE LIFF で再現する。
4. **シークレットはサーバーのみ**
   Claude API / LINE / ストレージのキーはサーバー側に隔離。クライアントへ露出しない（現行の最大の脆弱性を解消）。
5. **既存資産との互換**
   現行 HTML が出力する JSON をそのまま取り込めること（移行コストゼロを目指す）。

## 3. コンポーネント詳細

### 3.1 患者アプリ（PWA / LINE LIFF）
- 現行 `gyneco-daily-record` / `athlete-record` の入力体験を React 化。
- **オフラインファースト**: ローカル（IndexedDB）に保存 → オンライン時にサーバーへ同期（現行の localStorage 文化を踏襲しつつ消失リスクを排除）。
- LINE LIFF で起動した場合は LINE ユーザーと自動ひも付け（後述 3.6）。
- ケアプログラム（婦人科/アスリート…）に応じて入力フォームを動的生成（フォーム定義は API から取得）。

### 3.2 カルテ Web アプリ（先生用）
- 現行 `personal-karte` の機能を継承：基本情報 / 問題リスト / SOAP / 施術記録（visit）/ バイタル時系列 / 人体図（Canvas）/ メディア / AI チャット。
- 患者横断のダッシュボード・検索・集計を追加。
- 役割（オーナー/施術者/スタッフ）に応じた権限制御。

### 3.3 API / バックエンド（NestJS）
モジュール構成（= API 設計の単位、[03-api-design.md](03-api-design.md) と対応）:

| モジュール | 責務 |
|---|---|
| Auth | 先生のログイン（IdP/メール）、患者の LINE ログイン、JWT 発行 |
| Tenants | テナント（治療院）管理・プラン・メンバー招待 |
| Patients | 患者 CRUD・基本情報・同意・LINE ひも付け |
| Karte | ケアプラン（cover）・問題リスト・SOAP・施術記録（visit）・人体図 |
| Records | デイリーレコード（共通＋対象別）・服薬・セルフケア・トレーニング |
| Labs | 採血結果（手入力 / OCR 結果）・検査カタログ |
| Nutrition | 栄養目標・食事ログ・AI 食事解析 |
| Media | 画像/動画のアップロード（署名付き URL）・メタ管理 |
| Import | 既存 JSON の取り込み（移行・互換） |
| AIProxy | Claude API への安全な中継（OCR・食事解析・カルテ補助） |
| LINE | Webhook 受信・通知送信・LIFF 連携 |
| Audit / Consent | 監査ログ・同意管理 |

### 3.4 データベース（PostgreSQL）
- 共通カルテ基盤 ＋ 対象別モジュール ＋ 拡張可能な観測モデル（[02-database-design.md](02-database-design.md)）。
- RLS でテナント分離。保存時暗号化（at rest）、通信時暗号化（TLS）。

### 3.5 AI プロキシ（重要）
現行は **ブラウザから `api.anthropic.com` を直接叩いており、API キーがクライアントに露出**している。これをサーバー集約に変更する。

```
クライアント ──(画像/文脈)──▶ API /ai/* ──(サーバー保管のキー)──▶ Claude API
                                  │
                                  └─ ai_jobs テーブルに 入力参照・出力・トークン・コストを記録
```

- 用途: `lab_ocr`（採血OCR）, `food_analysis`（食事写真解析）, `karte_chat`（カルテ補助チャット）, `intake_scan`（問診票OCR）。
- レート制限・コスト上限・監査をサーバーで一元管理。
- モデルは設定で切り替え（現行 `claude-sonnet-4` 系を起点に、最新の Claude モデルへ更新可能に）。

### 3.6 LINE 連携（自動受信）
```
患者の LINE 操作 / LIFF アプリ ──▶ LINE Platform ──(Webhook)──▶ API /webhooks/line
                                                                   │
                                                  署名検証 → line_inbound_messages へ記録
                                                                   │
                                                  patient へひも付け → records へ反映 → 先生へ通知
```
- 患者は LINE ログインで本人確認。`line_user_id` を `patient` に保存。
- 現行の「JSON を手で送る」運用を、LIFF からのワンタップ同期 or Webhook 自動受信に置き換える。
- 移行期は「JSON 添付を受け取り → Import モジュールで取り込み」も併用可能。

## 4. 主要データフロー

### 4.1 患者の毎日の記録
1. 患者アプリで入力 → IndexedDB に即保存（オフライン可）。
2. オンライン時 `POST /patients/{id}/records`（冪等キー付き）で同期。
3. サーバーは共通レコード＋対象別フィールドを保存し、先生へ通知。

### 4.2 採血写真の取り込み（AI）
1. 患者/先生が画像アップロード → `POST /media`（署名付き URL）。
2. `POST /ai/lab-ocr`（media 参照）→ AIProxy が Claude へ → 構造化結果を返す。
3. 確認・修正の上 `POST /patients/{id}/labs` で確定保存。

### 4.3 先生の施術記録
1. `personal-karte` 相当の UI で visit を作成。
2. SOAP・取穴・手技・人体図マーク・バイタルを保存。
3. AI チャットは患者文脈（基本情報＋直近 visit）を `buildContext` 相当でサーバー側生成し、Claude へ。

### 4.4 既存 JSON の移行
1. 先生が現患者の JSON をアップロード → `POST /import/jobs`。
2. バージョン判定 → マッピング → 患者・レコード・採血・カバー情報を生成。
3. 取り込み結果（差分・警告）をレポート。詳細 [04-data-migration.md](04-data-migration.md)。

## 5. 環境構成

| 環境 | 用途 | データ |
|---|---|---|
| local | 開発 | 架空サンプルのみ |
| staging | 結合テスト・先生による受け入れ確認 | 匿名化データ |
| production | 本番運用 | 実データ（暗号化・監査・バックアップ必須） |

- シークレットは各環境のシークレットマネージャで管理（リポジトリには `*.env.example` のみ）。
- バックアップ: PostgreSQL 日次スナップショット ＋ PITR、オブジェクトストレージはバージョニング。

## 6. 非機能要件（NFR）

| 区分 | 目標 |
|---|---|
| 可用性 | 個人/小規模運用前提。月次 99.5% を当面目標 |
| 機密性 | 暗号化（at rest / in transit）、RLS、最小権限、監査ログ |
| 完全性 | マイグレーション管理、冪等な同期、論理削除＋監査 |
| 可搬性 | TypeScript + PostgreSQL の標準構成で引き継ぎ容易 |
| 拡張性 | ケアプログラム追加でスキーマ大改修不要（観測モデル） |
| 互換性 | 既存 HTML 出力 JSON を取り込み可能 |
